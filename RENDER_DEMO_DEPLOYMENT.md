# Danya Render demo deployment

This Blueprint creates three free Render resources in Frankfurt:

- `dania-storefront-alibadvi`: the public storefront
- `dania-vendure-alibadvi`: Vendure API, dashboard, and an in-process demo worker
- `dania-postgres-demo`: private PostgreSQL database

This setup is for a client demo. It is not the final production topology.

## 1. Verify locally

From the repository root:

```bash
npm ci
npm --prefix backend ci
npm run check
```

The check must finish without lint, type, test, storefront build, or Vendure dashboard build errors.

## 2. Push the reviewed files

Review the diff first:

```bash
git status
git diff --check
git diff
```

Then commit and push when you are satisfied:

```bash
git add .
git commit -m "Prepare secure Render demo deployment"
git push origin main
```

Do not commit a `.env` file or paste a real password into `render.yaml`.

## 3. Create the Render Blueprint

1. Sign in to Render and open **Blueprints**.
2. Choose **New Blueprint Instance**.
3. Connect GitHub if needed and select `Alibadvi/dania-commerce`.
4. Render will detect `render.yaml` in the repository root.
5. When prompted for `SUPERADMIN_PASSWORD`, enter a unique password of at least 16 characters. Store it in a password manager.
6. Apply the Blueprint and wait for all three resources to finish deploying.

`COOKIE_SECRET` is generated by Render. PostgreSQL credentials are injected from the database resource and are not stored in Git.

## 4. Verify the deployment

Open these URLs in order:

1. Vendure health: `https://dania-vendure-alibadvi.onrender.com/health`
2. Vendure dashboard: `https://dania-vendure-alibadvi.onrender.com/dashboard`
3. Storefront: `https://dania-storefront-alibadvi.onrender.com`

Dashboard credentials:

- Username: `superadmin`
- Password: the `SUPERADMIN_PASSWORD` entered during Blueprint creation

Run this smoke test:

1. Confirm the shop and PDP show the correct cropped demo shoes.
2. Select a size and add a product to the cart.
3. Register or sign in with a demo customer account.
4. Complete checkout with the clearly marked dummy payment flow.
5. Open **Orders** in the Vendure dashboard and confirm the order appears.
6. Edit a product name or stock value and confirm the storefront reflects it after refresh.

## 5. Understand the free-tier behavior

- Free web services sleep after 15 minutes without inbound traffic. The first request can take about a minute.
- Storefront and Vendure are separate free services. On a cold start, wait for Vendure's health URL to respond, then refresh the storefront.
- The free PostgreSQL database expires after 30 days and has no backups.
- Free web-service files are ephemeral. Demo seed images are restored on boot, but images uploaded later through the dashboard can disappear after a restart or sleep cycle.
- The two free web services share the workspace's monthly free instance-hour allowance.
- Do not enter real payment details, client secrets, or real customer data in this demo.

## 6. Before calling it production

Do not simply change the label from demo to production. First:

- move PostgreSQL to a paid plan with backups;
- use S3-compatible object storage or a persistent disk for assets;
- run the Vendure worker as a separate paid worker service;
- replace `DB_SYNCHRONIZE=true` with reviewed database migrations;
- disable dummy payments and install the real Iranian payment provider;
- configure SMTP and email verification;
- use a custom domain and update all three public URLs/origins;
- re-run dependency audits and a full checkout security test.
